# 0009 裁判席可暂停、掐断、终止对局；网页服务与实时推送的方式

> 起草日期：2026-09-15

- 状态：已采纳
- 日期：2026-09-15

## 背景

管理员界面（裁判席）从静态设计稿进入实现，需要定下三件事：管理员能不能在对局中途干预、干预到什么程度；浏览器怎样拿到实时进度；回放在哪一端切片。[decisions/0008](0008-admin-console-first.md) 只定了"先做管理员界面"，这些都留作未决。

## 决定

- **两段式暂停。** 暂停键按第一下是软暂停：裁判在下一次向任何玩家发通知前停住，进行中的模型调用跑完并正常记录。等待期间再按一下是掐断：进行中的调用立刻作废，玩家线程回滚到发通知之前，如同这份通知从未发出；继续后原样重发同一份通知。作废的调用记一条 `voided_call` 事件，模型侧可能仍会计费。
- **终止立刻生效。** 终止总是掐断进行中的调用，不等它们返回。终止的对局保留已落盘的全部内容，结果记为"已终止、无胜方"，出现在对局列表里，不计入胜负类统计。
- **暂停时长从用时里扣除。** 只算"没有任何调用在跑、纯等待"的时间，另记为暂停时长；软暂停等调用返回的那段仍算对局用时。
- **服务端到浏览器用 SSE，不用 WebSocket。** 每局一条事件流，新事件产生即推送，断线后浏览器带上最后一条事件序号续传。控制操作是普通请求。
- **回放在浏览器本地切片。** 页面拿到整局事件列表后，按序号截断再归约出画面；已结束与进行中的局走同一条路径，服务端不做切片接口，也不再重新调用模型。
- **每局是服务进程里的一个线程**，同时最多若干局，多出的排队；服务进程退出时未打完的局记为"已中断"，不恢复。
- **前端是纯静态文件**，不引入前端框架与打包工具，由同一个服务进程提供。

## 后果

- 裁判在每次发通知前多一个检查点，进行中的调用要能被外部掐断；这两处改动都在裁判与模型客户端内部，规则代码不变。
- 玩家线程"整局只增不删"多了一个例外：被掐断的通知会被撤回。撤回后线程与从未发过这份通知时完全一致，模型不会看到任何痕迹。
- 事件流新增 `ask`、`voided_call` 与暂停、继续、终止、出错几类控制事件；结果文件新增状态、暂停时长、作废调用数。
- 每个打开的页面在服务端占一个等待线程；单人使用的管理工具可以接受。

## 备选方案

- **只做软暂停**：实现最简单，但隐藏思考开着时一次调用可能要等一分钟，管理员没有办法立刻停下来。
- **只做硬掐断**：每次暂停都作废一次调用，浪费已花的钱；且作废对同时进行的五路投票影响更大。
- **终止等进行中的调用返回**：多等一次调用没有意义，对局已经不要了。
- **WebSocket**：双向能力用不上，且浏览器端的自动重连与续传要自己写。
- **服务端切片接口**：多一个接口，前端仍要有归约逻辑；不如一次拿全事件在本地切。
- **每局一个子进程**：崩溃隔离更好，但暂停、掐断都要跨进程传递，实时事件也要靠读文件；线程方案下一局挂掉只影响它自己（异常被捕获并落盘为"出错"）。
